# Contributing

This is a worked example, not a general framework — and it's meant to be pulled apart, not just read. A few ways to engage, roughly lightest to heaviest:

**Open an issue.** The lowest-friction way to contribute. Disagree with how a Workflow is scoped, see a gap in the Evidence, or have a real scenario where this model doesn't hold up — open an issue and describe it in plain language. No particular format required.

**Comment on an existing issue.** If your feedback relates to something already open, adding your perspective there keeps the discussion in one place.

**Propose a new pressure test.** The examples/ folder is meant to grow. If you have a real (or realistic, anonymized) scenario that would stress-test this model in a new direction — a different grant structure, a different regulatory regime, a different failure mode — fork the repo, add a file under examples/ following the structure of pressure-test.md, and open a pull request.

**Propose a change to the model.** If a Workflow, Execution Plan, or Field Readiness definition in the README should change, open a pull request with the edit and a short explanation of what scenario motivated it.

## Ground rules

Plain language first. If a proposed change can't be explained to a non-technical operations person, it needs more work before it's ready.

Real scenarios over hypotheticals. Feedback grounded in something that actually happened is more useful than abstract critique.

Disagreement is welcome. The point of sharing this early is to find where it's wrong.

For the underlying concept vocabulary — Business Problem, Initiative, Workflow, Execution Plan, Field Readiness — see business-enablement-concept-model (https://github.com/AC-tech-alt/business-enablement-concept-model).
